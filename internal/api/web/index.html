How filtering actually behaves
  • Attribute keys are case-sensitive (realName, not realname). Only name and slug are matched case-insensitively.
  • Values are compared case-insensitively but must match exactly — there is no partial match, no search, and no sorting.
  • An unrecognised key yields zero results rather than an error.
  • Array attributes (e.g. powers) are stringified as [flight telekinesis], so they are effectively unfilterable.

Endpoint reference

GET /

Content-negotiated. Browsers get this console; every other client gets a JSON discovery document listing each loaded entity type.

curl localhost:8080/            # JSON
curl localhost:8080/?format=json  # JSON, from a browser

GET /console

This page, served unconditionally regardless of the Accept header.

GET /api/v1/types

Every discovered entity type and its record count.

curl localhost:8080/api/v1/types

GET /api/v1/{type}

List entities, paginated and optionally filtered.

  • limit — default 20, clamped to 100
  • offset — default 0
  • any other parameter is an equality filter on name, slug, or an attributes field
curl "localhost:8080/api/v1/characters?affiliation=Avengers&limit=5"

GET /api/v1/{type}/{idOrSlug}

A single entity by numeric id or by slug.

curl localhost:8080/api/v1/characters/iron-man

PUT /api/v1/admin/{type}

Replaces a type's entire dataset in memory, creating the type if it does not exist. Deliberately not wired to a button on this page: the endpoint is unauthenticated, so a control here would let any visitor wipe the live dataset. Changes are in-memory only and revert on restart.

curl -X PUT localhost:8080/api/v1/admin/items \
  -H 'Content-Type: application/json' \
  -d '[{"id":1,"name":"Elixir","potency":"high"}]'
